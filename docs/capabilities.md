# 归根电池养护功能复核

这次用三个实际问题决定是否继续加功能：能否在正确的电量和温度下改变充电，系统重启或断连后能否恢复，以及用户能否验证效果。覆盖日常通勤、长时间接电、原厂无 root 手机、外部插座和养护记录。使用者已有的 50%–75% 策略贯穿下面各项。

| 使用场景 | 产品选择与理由 |
| --- | --- |
| 到上限即停、回落才充 | ACC 在手机上执行。兼容的 Shizuku 驱动可选择前台巡航。插拔保留阶段，手动提前补电只影响这一轮。读取到模式和 Android 实际报告的充电状态分别展示。 |
| 固件有上下限、没有通用暂停开关 | Shizuku 分别核对唯一内置电池的标准起充与停充阈值。只提供一端就只展示该端，写入后重新读取。可撤销上一次已确认的改动，撤销前会核对电池身份和两端现值。固件的百分比取整、复充边界、重启持久性由驱动决定。 |
| 原厂手机没有写权限 | 本机提醒、原厂电池设置和可选的外部自动化覆盖三种需求。LineageOS 有可用的原生限充页时可以直接进入。外接插座具有自己的开关与失联策略，真机旁路供电则需要手机硬件支持。 |
| 异常发热或长时间停留在高电量 | ACC 执行其温控，Shizuku 提供温度滞回提醒或由兼容驱动执行。24 小时、7 天和 30 天的暴露时长及其重叠可以评估一项改动是否改善了实际使用。 |
| 日常通勤和临时提前补电 | ACC 版可以手动提前一轮，或预约今天／次日的一个开始时间；补电仍服从原上限与温控。预约只在一小时窗口内有效，到上限或自然跌到下限即结束。实际电量取决于供电、温度和充电速率。 |
| 重启、更新、撤权或驱动下线 | 谁实际控制充电就读回谁的状态。ACC 前台复核守护进程，已停止时可手动启动。Shizuku 本地记录可恢复，硬件控制另行确认 shell 会话；休眠、关机及强制停止会造成观测缺口。 |
| 比较不同时间段或充电环境 | 同口径比较接电时长、系统充电时长、首末电量、峰值温度及可用的剩余电荷净变化。支持 CSV 进一步分析；保留缺测和断点。仅凭电池端读数无法鉴定线材额定功率。 |
| 个性化和家庭自动化 | 指定接收应用可读取当前策略与阈值，触发用户配置的自动化。无需在归根维护每个插座的专用协议、账号和云服务。 |
| 强制深放电与定期校准 | 可能帮助有电量估算偏差的特定设备。已有正常读数的手机没有通用的校准需求，手动频繁执行还会消耗充放电循环。保留厂商自己的校准流程。 |
| 固定 100% 旅行档、电价或地理围栏、预测到点满电 | 属于带有用户出行、位置、电价或特定续航目标的策略。维持设定上限是归根默认承诺；选择其他上限可由用户或支持的原厂方案显式设置。没有足够充电速率样本时，不给出精确到点承诺。 |
| 绕过电池、直接限压限流、关机保护、反向供电 | ACC 和手机固件已有部分专有能力。需要按型号确认电芯拓扑、节点单位、温控和恢复手段；通用前端不把模糊节点包装成可移植的开关。 |
| 电池健康百分比、剩余寿命天数、自动退役 | 展示系统或驱动可提供的健康分类、循环次数和容量。窄幅循环、双电芯及缺失计数使单次观测不足以推算整包寿命；保留原始来源与可导出记录。 |
| 每应用耗电、阻止休眠、Mac 电源灯、云端设备群与组件外观 | 应用耗电已有系统统计入口；阻止休眠另有耗电影响。Mac 专用硬件、设备管理和外观定制不改善 Android 手机的阈值执行或测量。 |

## 兼容性与验证边界

- 通过上游 ACC 实际守护逻辑的调度测试，以及模拟驱动、配置、服务状态的回归。通过 Android 模拟器验证状态、Binder 和升级路径。实际执行了两次系统重启，并核对从正式 Shizuku 1.0 升到 1.1 时旧记录完整、旧电荷字段为空、新采样可写入。
- Shizuku 的硬件正向写入由可控的驱动替身覆盖。读数随设备变化，驱动接受写入只是控制面的证据，电池物理电流还需设备测量。已连接的一加 8T 在先前的普通 shell 检查中没有暴露标准充电行为开关。
- 使用独立接收端在 Android 模拟器上验证状态共享权限、温控和手动例外。实际插座通断、厂商休眠策略、不同内核对原生阈值的解释需要对应设备验证。
